# 交易双方评价功能增量设计 v1.0

> [文档总目录](../README.md) · 05-交易双方评价

## 1. 目标与口径

二手交易或跑腿订单完成后，双方各可给对方提交一次 1～5 星评分。评分以**被评价人在该笔订单中的身份**计入其个人评分，公开展示平均分和评价数。

| 订单 | 评价人 | 被评价人 | 计入被评价人的栏目 |
| --- | --- | --- | --- |
| 二手交易 | 买家 | 卖家 | 卖方／服务方评分 |
| 二手交易 | 卖家 | 买家 | 买方／需求方评分 |
| 跑腿 | 发布者 | 接单者 | 卖方／服务方评分 |
| 跑腿 | 接单者 | 发布者 | 买方／需求方评分 |

跑腿按服务交易理解：发布者是需求方，接单者是服务方。数据库统一使用 `buyer`、`seller` 两个被评价身份；界面显示“买方／需求方”“卖方／服务方”。两人可独立评价，提交后立即计入平均分；无需等待对方。首版只提交整数星级，不含文字评论和改分功能。历史已完成订单也可评价。

无评价时 `average=null, count=0`，页面显示“暂无评价”，不显示默认 5 星。平均分取该身份收到的所有有效评价的算术平均值，展示到 1 位小数，同时显示评价数。例如 `4.7（12 人评价）`。买方和卖方评分分别计算，不合成一个总分。

## 2. 与现有系统的衔接

- 二手订单以 `product_order.status='completed'` 为评价前提。现有 `PUT /api/product-orders/{id}/complete` 由买家确认收货。
- 跑腿以 `task_order.status='completed'` 为评价前提。现有 `PUT /api/tasks/{id}/complete` 由发布者确认完成；当前实现还允许从 `accepted` 直接完成，评价规则照样以最终的 `completed` 为准。
- 评价绑定 `product_order.id` 或 `task_order.id`。两种订单都可能因终止产生同一商品／任务的多条历史订单，因此不能按 `product.id` 或 `task.id` 去重。
- 软删除不删除订单和评价。已完成任务的公开详情仅参与者可见，发布者软删除后任务详情不可访问；评价入口必须以订单记录为准，不能依赖任务／商品详情页是否仍可打开。
- `web/js/task-detail.js` 当前通过遍历“我接取的任务”判断接单方，且任务详情没有稳定返回 `orderId`；评价相关身份和订单 ID 由后端直接提供，页面不再推断。

## 3. 数据库

新增 `rating` 表，字段建议如下：

```sql
CREATE TABLE rating (
    id                INTEGER PRIMARY KEY AUTOINCREMENT,
    product_order_id  INTEGER REFERENCES product_order(id),
    task_order_id     INTEGER REFERENCES task_order(id),
    reviewer_id       INTEGER NOT NULL REFERENCES user(id),
    reviewee_id       INTEGER NOT NULL REFERENCES user(id),
    reviewee_role     TEXT NOT NULL CHECK (reviewee_role IN ('buyer', 'seller')),
    stars             INTEGER NOT NULL CHECK (typeof(stars) = 'integer' AND stars BETWEEN 1 AND 5),
    created_at        TEXT NOT NULL DEFAULT (datetime('now', 'localtime')),
    CHECK ((product_order_id IS NOT NULL) <> (task_order_id IS NOT NULL)),
    CHECK (reviewer_id <> reviewee_id)
);
CREATE UNIQUE INDEX uq_rating_product_reviewer
    ON rating(product_order_id, reviewer_id) WHERE product_order_id IS NOT NULL;
CREATE UNIQUE INDEX uq_rating_task_reviewer
    ON rating(task_order_id, reviewer_id) WHERE task_order_id IS NOT NULL;
CREATE INDEX idx_rating_reviewee_role ON rating(reviewee_id, reviewee_role);
```

订单身份、双方用户 ID 和 `reviewee_role` 均由服务端根据订单计算，不接收客户端传值。平均分和数量直接对 `rating` 聚合，不在 `user` 表存冗余分数。将建表语句加入 `backend/db/schema.sql`，并把 `rating` 放在 `backend/db/init_db.py` 的订单表之前删除。对现有 `app.db` 提供独立、只增表和索引的迁移 SQL；`init_db.py` 会清空并重建数据库，不能用于生产数据迁移。

## 4. 后端接口契约

沿用项目 `Result{code,msg,data}` 包装和 session 身份。`stars` 只接受 JSON 整数 `1..5`，例如 `{"stars":5}`。

| 接口 | 权限 | 用途 |
| --- | --- | --- |
| `POST /api/product-orders/{id}/rating` | 登录，订单买家或卖家 | 给本订单另一方评分 |
| `POST /api/task-orders/{id}/rating` | 登录，订单发布者或接单者 | 给本订单另一方评分 |
| `GET /api/task-orders/{id}` | 登录，仅订单双方 | 读取跑腿订单标题、双方身份和本人的评价状态；任务软删除后仍可读取订单历史 |
| `GET /api/me/rating-orders?state=all\|pending&page=1&size=20` | 登录 | 分页读取本人已完成的两类订单及评价状态，供“待评价／评价记录”使用 |
| `GET /api/public/users/{id}/rating` | 公开 | 返回用户公开资料和两栏评分汇总 |

`POST` 成功示例：`{"id":31,"stars":5,"revieweeId":7,"revieweeRole":"seller"}`。服务端读取订单后校验完成状态、参与者身份，确定对方 ID 与身份，在同一事务插入评价。数据库唯一索引保证并发点击也只产生一条。不存在返回 `404`；未登录 `401`；非参与者 `403`；星级非法 `400`；订单未完成或已评价 `409`。

`GET /api/public/users/{id}/rating` 示例：

```json
{
  "userId": 7,
  "username": "小李",
  "avatarUrl": "/uploads/avatar.png",
  "buyer": {"average": 4.8, "count": 6},
  "seller": {"average": 4.6, "count": 11}
}
```

该公开接口只返回昵称、头像和评分，不复用含账号及联系方式的 `User` 对象。二手订单详情 `GET /api/product-orders/{id}` 增加 `myRatingStars` 和 `counterpartyRating`；跑腿订单详情返回同名字段及 `viewerRole`（`publisher`／`accepter`）。`/api/me/rating-orders` 每项包含 `kind`、`orderId`、`title`、`counterpartyId`、`counterpartyName`、`finishedAt`、`myRatingStars`，从订单表查询，以免软删除导致记录消失。

商品和任务列表／详情已有卖家或发布者 ID，给这些查询批量补充对应身份的 `ratingAverage`、`ratingCount`。使用聚合 JOIN 或一次批量查询，避免每张卡片单独请求。跑腿进行中时，参与者可从订单详情读取对方评分；商品卖家在订单页可看到买家评分。

实现位置：新增 `RatingDAO`、`RatingService`、`RatingController`、评价 DTO／展示 DTO；补充 `ProductOrderDAO`、`TaskOrderDAO` 的订单详情查询，以及 `ProductDAO`、`TaskDAO` 的公开评分字段查询。身份和状态规则集中在 `RatingService`，Controller 只读取 session 用户并传入订单 ID、星级。

## 5. 前端页面

1. `product-order.jsp`／`web/js/product-order.js`：订单完成后显示对方姓名、对方对应身份的公开评分和 1～5 星选择器。未评价显示“提交评价”，提交成功后更新为“已评价 5 星”。订单进行中只展示对方现有评分。
2. 新增 `task-order.jsp`／`web/js/task-order.js`：展示跑腿完成记录与同一套评分组件。`task-detail.jsp` 在参与者可见时提供进入本次订单的链接；不依赖任务详情页执行评价。
3. `profile-user.jsp`／`web/js/profile.js`：资料区显示本人两栏评分；记录区增加“待评价／评价记录”入口，读取 `/api/me/rating-orders`，按分页展示二手和跑腿已完成订单，评价后更新当前条目。已软删除的资源也保留订单入口。
4. 商品列表、商品详情、任务列表、任务详情在卖家或发布者姓名旁显示对应身份的平均分和评价数；姓名链接到新增 `user-rating.jsp`／`web/js/user-rating.js`，只展示公开资料和评分。订单页展示交易对方的对应身份评分，保证双方在交易过程中都能看到对方信誉。
5. 抽取 `web/js/rating.js` 和 `web/css/rating.css` 供订单页复用。星级选择用带文字标签的单选按钮，支持键盘操作；请求中禁用提交按钮，失败展示接口错误，成功后重新读取订单和评分。所有动态昵称经现有 `api.escapeHtml` 输出。

## 6. 实施顺序与验收

1. 先更新增量接口契约，明确身份映射、空评分格式和错误码。
2. 增加数据库迁移、DAO、Service、Controller；使用临时 SQLite 库验证迁移和查询。
3. 接入二手订单、跑腿订单、个人空间和公开评分展示；最后补充列表批量查询。
4. 验收四个评价方向：买家评卖家、卖家评买家、发布者评接单者、接单者评发布者。检查 1／5 星边界、非整数、未完成、已终止、非参与者、重复提交、并发重复提交、软删除后的历史评价，以及两栏平均分和评价数。

本方案将跑腿评价与二手交易合并为同一组“需求方／服务方”信誉。若产品需要分别展示“二手买家、二手卖家、跑腿发布者、跑腿接单者”四栏，只需将聚合维度改为订单类型加角色，订单与评价绑定方式不变。
