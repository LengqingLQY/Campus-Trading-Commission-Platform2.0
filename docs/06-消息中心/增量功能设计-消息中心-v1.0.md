## 1. 目标与首版范围

用户登录后，可以从侧边栏查看未读数量，进入消息中心阅读通知，并跳转到发布记录或订单继续处理。通知由现有业务操作成功后自动生成，接收者离线时仍保存，重新登录后可查看。

首版包含：

1. 审核通过、审核驳回通知。
2. 商品被购买、任务被接取、商品已交付、任务已送达和订单完成通知。
3. 终止申请发起、撤回、拒绝和同意通知。
4. 消息分页、分类筛选、全部／未读筛选、单条已读和全部已读。
5. 侧边栏未读角标、定时刷新、关联页面跳转和返回消息列表。

订单完成通知同时提醒双方评价，不另外生成一条“待评价”消息。通知中的评价提示是发生时的内容，是否仍可评价以订单页的实时状态为准。

后续版本再考虑评论与回复通知、收到评价通知、私信聊天、管理员公告、通知偏好、消息删除、浏览器推送、短信和邮件。首版不补发上线前的历史业务消息，不因用户登录或刷新列表重复生成提醒。

## 2. 现有系统与衔接原则

| 现有能力 | 当前实现与本次衔接 |
| --- | --- |
| 技术结构 | JSP + 原生 JavaScript，Spring Boot + JdbcTemplate，SQLite |
| 登录与接口 | session 身份；沿用 `Result{code,msg,data}` 和现有 `AuthInterceptor` |
| 发布审核 | 商品和任务发布／修改后进入 `pending`，由 `AdminService` 审核；旧版接口契约中的“直接审核通过”说明已不代表当前代码 |
| 二手订单 | `ProductService` 管理购买、交付、完成和终止；订单详情与操作入口为 `product-order.jsp` |
| 跑腿订单 | `TaskService` 管理接取、送达、完成和终止；`task-order.jsp` 当前主要展示订单和评价，业务操作仍在任务详情页 |
| 双方评价 | 已完成订单可评价；通知复用现有订单页的评价入口 |
| 软删除 | 订单历史保留；通知独立保存文字快照，关联资源删除后消息仍可读 |

消息是业务事件记录，不是待办状态。标记已读只表示用户读过通知，不代表已同意终止、确认收货或提交评价。旧通知保留当时的内容，打开目标页后按最新业务状态显示可用操作。

同一商品或任务在终止后可能再次成交／接单，订单通知必须保存**当次订单 ID**，不能在点击时按商品／任务 ID 查“最新订单”。

## 3. 通知事件与接收规则

### 3.1 审核通知

| 消息类型 `type` | 触发时机 | 接收者 | 标题示例 | 跳转目标 |
| --- | --- | --- | --- | --- |
| `audit_approved` | 商品或任务审核结果实际变为通过 | 发布者 | 商品审核已通过／任务审核已通过 | 对应个人发布记录 |
| `audit_rejected` | 审核结果实际变为驳回，或驳回理由发生变化 | 发布者 | 商品审核未通过／任务审核未通过 | 对应个人发布记录 |

正文包含资源标题；驳回时包含完整审核理由，例如：`你发布的《高等数学教材》未通过审核。原因：图片不清晰，请补充实物照片后重新提交。`

同一审核状态、同一审核理由的重复提交不新增消息。发布者修改后重新进入待审核，再次审核可生成新的结果通知。管理员调整已有审核结果时，也按实际变化生成通知；首版不额外限制管理员只能审核待审核内容。

### 3.2 订单进度通知

| 消息类型 `type` | 业务事件 | 接收者 | 标题／正文重点 |
| --- | --- | --- | --- |
| `order_created` | 买家成功购买商品并创建订单 | 卖家 | 商品被购买，请与买家约定交付 |
| `order_created` | 接单者成功接取任务并创建订单 | 发布者 | 任务已被接取，可查看本次订单 |
| `order_delivered` | 卖家确认交付，二手订单进入 `delivered` | 买家 | 商品已交付，请核对后确认收货 |
| `order_delivered` | 接单者标记送达，跑腿订单进入 `delivered` | 发布者 | 任务已送达，请核对后确认完成 |
| `order_completed` | 二手订单进入 `completed` | 买家和卖家各一条 | 交易已完成，可以为对方评价 |
| `order_completed` | 跑腿订单进入 `completed` | 发布者和接单者各一条 | 跑腿已完成，可以为对方评价 |

正文包含当次商品／任务标题、订单编号及必要的动作说明。首版不在消息正文放入手机号、微信、QQ、取送详细地址等联系方式，交易资料继续由原业务页面提供。

购买者、接单者和交付者已在操作页面获得成功反馈，不另外给自己发送同事件通知。**订单完成是例外**：双方均需要后续评价入口，因此给双方各发一条完成通知。

跑腿现有业务允许从 `accepted` 直接确认完成，此时直接生成完成通知，不补造一条“已送达”通知。

### 3.3 终止申请通知

以下规则同时适用于二手和跑腿：

| 消息类型 `type` | 触发时机 | 接收者 | 标题／正文重点 |
| --- | --- | --- | --- |
| `termination_requested` | 终止申请成功创建为 `pending` | 订单另一方 | 对方申请终止，请进入业务页面处理；附完整申请理由 |
| `termination_withdrawn` | 发起者将申请撤回为 `withdrawn` | 原接收方 | 对方已撤回申请，查看订单当前进度 |
| `termination_rejected` | 另一方将申请拒绝为 `rejected` | 申请发起者 | 对方拒绝终止，查看订单当前进度 |
| `termination_approved` | 另一方同意，申请与订单状态更新成功 | 申请发起者 | 对方同意终止，本次订单已终止 |

处理者获得页面成功反馈，不再给自己发一条结果消息。原申请通知不会因撤回、拒绝或同意而被删除，也不会被自动标为已读。

跑腿终止申请当前按 `task_id` 保存。本次生成通知时，要在事务中取得当时的 `task_order.id` 并保存为消息目标；同意终止时使用取消前已取得的原订单 ID，不在任务恢复 `open` 后重新查找订单。

### 3.4 分类与数量

界面分类固定为“全部、审核、订单、终止申请”，分别传 `category=all|audit|order|termination`。分类由上表的 `type` 映射，不在数据库额外保存一份分类。

每个成功事件按接收者生成独立消息。一次订单完成生成两条，其他事件通常生成一条。服务端根据发布者、订单双方及申请发起者确定接收者，客户端不提交接收人、消息类型或通知正文。

## 4. 页面与交互

### 4.1 消息中心入口

在 `web/sidebar.jsp` 中“个人空间”前增加“消息中心”，链接到 `message-center.jsp`，当前页使用 `app-page--messages` 标识。普通用户和管理员均可查看自己的消息，管理员角色不会获得查看其他用户消息的权限。

未读数为 0 时隐藏角标，1～99 显示实际数量，超过 99 显示 `99+`；辅助文字仍说明实际未读数量。游客隐藏未读角标且不轮询，点击入口按现有登录流程保留目标地址。

### 4.2 页面结构

```text
消息中心                              未读 5 条  [全部已读]
审核结果、订单进度和终止申请都在这里

[全部] [审核] [订单] [终止申请]         [全部消息] [仅未读]

● [终止申请] 对方申请终止交易          2026-10-20 14:30
  《高等数学教材》订单 #23：对方申请终止，原因：交接时间无法协调。
  [查看订单] [标为已读]

  [订单] 跑腿已完成                    2026-10-20 13:10
  《代取快递》订单 #18 已完成，你可以为对方评价。
  [查看订单]

                         [上一页] 第 1 / 3 页 [下一页]
```

每条消息显示分类、标题、完整正文、时间和未读标识。正文较长时自然换行，首版不另建消息详情页。时间沿用项目 `YYYY-MM-DD HH:mm:ss` 字符串格式和现有格式化方法。

- 默认显示全部分类、全部消息，每页 20 条，按 `created_at DESC, id DESC` 排序。
- 切换分类或已读筛选回到第 1 页；查询参数保留 `category`、`state`、`page`，便于刷新和返回。
- 打开列表不自动已读。点击“标为已读”成功后更新该条样式和全局未读数。
- 点击“查看订单／查看发布记录”时，先标记该消息已读，成功后在当前标签打开关联页面。已读写入失败则保留当前页并显示重试提示，不提前改变角标。
- 在“仅未读”列表标记已读后，重新获取当前页；当前页已无记录且超出末页时，回到最后一个有效页。
- “全部已读”作用于当前用户的所有分类，而非当前页或当前筛选。提交期间禁用按钮，完成后重新加载列表与角标。
- 无消息显示“暂时没有消息”；仅未读为空显示“没有未读消息”；读取失败显示错误和重试入口，不展示为空列表。
- 控件使用链接和按钮，支持 Tab／Enter 操作；未读状态同时用文字和视觉标记表达。

### 4.3 跳转约定

数据库保存 `target_type` 和 `target_id`，接口返回 `targetType` 和 `targetId`。首版只使用下面四种目标，不保存客户端提供的 URL。

| `targetType` | `targetId` 含义 | 前端页面 |
| --- | --- | --- |
| `product_record` | 商品 ID | `profile-user.jsp?recordTab=published-products#profile-records` |
| `task_record` | 任务 ID | `profile-user.jsp?recordTab=published-tasks#profile-records` |
| `product_order` | 当次二手订单 ID | `product-order.jsp?orderId={targetId}` |
| `task_order` | 当次跑腿订单 ID | `task-order.jsp?orderId={targetId}` |

审核通知统一进入个人发布记录，保证驳回内容也有可访问入口；首版不承诺自动定位某一条发布记录，完整驳回理由可直接在消息中阅读。

订单页保留“返回消息中心”入口，使用现有 `returnTo`、`api.pageUrlWithReturn` 和 `api.safePageUrl` 传递／读取来源，保留消息筛选与页码。`profile.js` 也需补充来自消息中心时的返回入口。

跑腿订单页需补充“进入任务处理”链接：仅当**该订单自身**状态为 `accepted`／`delivered` 时显示，跳到 `task-detail.jsp?taskId={order.taskId}`。用户可在那里送达、完成或处理终止申请；已完成订单直接在订单页评价，已终止订单只展示历史，不链接到新一轮接单处理。

通知不会自动执行任何交易操作。目标页面继续调用现有接口确认身份与最新状态；内容被删除或已不可访问时，保留消息正文，目标页展示不可访问提示和返回消息入口。

## 5. 数据库设计

新增 `notification` 表，一条记录代表一位用户收到的一条消息。

```sql
CREATE TABLE IF NOT EXISTS notification (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    recipient_id  INTEGER NOT NULL REFERENCES user(id),
    type          TEXT NOT NULL CHECK (type IN (
                      'audit_approved', 'audit_rejected',
                      'order_created', 'order_delivered', 'order_completed',
                      'termination_requested', 'termination_withdrawn',
                      'termination_rejected', 'termination_approved'
                  )),
    title         TEXT NOT NULL,
    content       TEXT NOT NULL,
    target_type   TEXT NOT NULL CHECK (target_type IN (
                      'product_record', 'task_record', 'product_order', 'task_order'
                  )),
    target_id     INTEGER NOT NULL,
    read_at       TEXT,
    created_at    TEXT NOT NULL DEFAULT (datetime('now', 'localtime'))
);

CREATE INDEX IF NOT EXISTS idx_notification_recipient_time
    ON notification(recipient_id, created_at DESC, id DESC);
CREATE INDEX IF NOT EXISTS idx_notification_unread_time
    ON notification(recipient_id, created_at DESC, id DESC)
    WHERE read_at IS NULL;
```

- `read_at IS NULL` 为未读；非空为首次标记已读时间。不增加独立 `is_read` 字段，接口计算布尔值 `read`。
- 标题和正文是事件发生时生成的文字快照，资源改名、审核理由变化或软删除都不改写旧消息。
- `target_id` 是按目标类型解释的关联 ID，不是统一外键。删除资源不级联删除消息。
- 不在用户表存未读数量，每次按接收者统计。首版不增加事件总线、消息队列或通用事件表。

迁移新增 `backend-java/src/main/resources/db/migrations/002-notification.sql`，只增加表与索引。将其加入 `spring.sql.init.schema-locations`，保留原有 `001-rating.sql`；同步更新 `backend/db/migrate_db.py`，按顺序执行两份增量迁移。

全新库同步更新 `backend/db/schema.sql`；`init_db.py` 重建时在删除 `user` 前删除 `notification`。已有库通过增量迁移保留数据，迁移后消息表为空，不使用初始化脚本升级。

## 6. 接口契约

全部接口需要登录，用户身份从 session 取得。成功 HTTP 200，包装 `{"code":0,"msg":"success","data":...}`；具体成功文案沿用现有 `Result.ok`。

| 接口 | 参数／请求体 | 用途 |
| --- | --- | --- |
| `GET /api/me/notifications` | `category=all&state=all&page=1&size=20` | 分页读取本人消息 |
| `GET /api/me/notifications/unread-count` | 无 | 读取本人全局未读数量及消息水位 |
| `PUT /api/me/notifications/{id}/read` | 无请求体 | 将本人的单条消息标为已读 |
| `PUT /api/me/notifications/read-all` | `{"upToId":103}` | 将指定水位及之前的本人消息全部标为已读 |

### 6.1 消息列表

- `category`：`all`（默认）、`audit`、`order`、`termination`。
- `state`：`all`（默认）、`unread`。首版不单独提供“仅已读”。
- `page`：默认 1，正整数；`size`：默认 20，整数 1～50。
- 超出末页返回空 `list` 和实际 `total`，不改写请求页码。

返回示例中的 `data`：

```json
{
  "list": [
    {
      "id": 103,
      "type": "termination_requested",
      "category": "termination",
      "title": "对方申请终止交易",
      "content": "《高等数学教材》订单 #23：对方申请终止，原因：交接时间无法协调。",
      "targetType": "product_order",
      "targetId": 23,
      "read": false,
      "createdAt": "2026-10-20 14:30:00"
    }
  ],
  "total": 37,
  "page": 1,
  "size": 20,
  "unreadCount": 5,
  "latestId": 103
}
```

`total` 是当前分类与状态条件下的消息数；`unreadCount` 和 `latestId` 始终覆盖本人所有分类。`latestId` 为该用户当前最大消息 ID，无消息时为 0。`readAt` 未读时按现有 `non_null` 配置省略，已读时返回时间；`read` 始终返回。

采用新增 `NotificationPage` 返回对象，沿用现有 `PageResult` 的四个分页字段，再补 `unreadCount`、`latestId`，不修改其他列表接口。列表与计数在同一次只读事务中读取。

### 6.2 未读数量

`data` 示例：`{"unreadCount":5,"latestId":103}`。数据库真实数量完整返回，由前端决定是否显示 `99+`。

### 6.3 标记已读

单条：按 `id` 和 session 用户 ID 查询归属，对本人未读消息写入 `read_at`；重复标记返回成功且不改写首次已读时间。不存在或不属于本人统一返回 `404`。成功 `data` 返回 `{"id":103,"read":true,"readAt":"2026-10-20 14:31:00"}`。

全部：`upToId` 为非负 JSON 整数，使用最近一次列表或未读数量响应的 `latestId`。只更新 `recipient_id=当前用户 AND read_at IS NULL AND id<=upToId`，返回 `{"updatedCount":5}`；0 或重复操作可以更新 0 条并返回成功。

水位用于明确“全部”的时间范围：用户点击前已拉取的消息标为已读，点击期间新产生且 ID 更大的消息保留未读。首版不引入分页游标或额外同步协议。

写入成功后，消息页重新读取当前列表获得最新数量；其他页面的单条操作完成后读取未读数量。角标不依赖前端直接减一。

### 6.4 错误与权限

| HTTP／业务码 | 场景 |
| --- | --- |
| `400` | 分类、状态、分页、水位或路径 ID 的格式／取值不合法 |
| `401` | 未登录或 session 过期 |
| `404` | 单条消息不存在或不属于当前用户 |
| `500` | 数据库或服务异常，沿用现有统一错误处理 |

不提供按 `userId` 查询、不提供客户端创建消息、不提供修改消息正文的接口。关联订单仍使用原接口的权限规则，消息已读不能作为访问订单的授权凭据。

## 7. 消息生成与事务

首版在业务 Service 中同步写入消息，与原业务变更共用同一个数据库事务。业务状态变更成功后再插入通知，事务提交后对其他请求可见；任一步失败则整体回滚，接口不返回成功。

```text
请求进入原业务 Service
    → 按现有业务规则确定本次状态变更
    → 更新状态／创建订单或申请，取得当次 ID
    → 根据业务记录确定接收者和消息文字
    → 插入 notification（完成事件为双方各插入一条）
    → 提交事务并返回原有业务响应
```

接入位置：

| 类／方法 | 接入内容 |
| --- | --- |
| `AdminService.auditProduct/auditTask` | 审核结果实际变化后通知发布者；补事务边界 |
| `ProductService.buyProduct` | 取得新订单 ID 后通知卖家 |
| `TaskService.acceptTask` | 取得新订单 ID 后通知发布者 |
| `ProductService.deliverProductOrder`、`TaskService.deliverTask` | 成功进入交付／送达状态后通知对方 |
| `ProductService.completeProductOrder`、`TaskService.completeTask` | 订单完成后给双方生成完成与评价提示 |
| 两个 Service 的 `create/withdraw/reject/approveTerminationRequest` | 申请状态变化后生成对应通知；缺少事务的方法补事务边界 |

新增 `NotificationDAO`、`NotificationService`、`NotificationController`、消息与返回 DTO。`NotificationService` 负责类型映射、模板和读写规则，仅依赖 DAO，不反向依赖交易 Service，避免循环注入；业务 Service 传入已确定的订单、接收者和必要文字。

订单进度和终止申请仅在现有带状态条件的更新成功后生成消息，失败或重复操作不生成。审核 DAO 需使“状态和理由均未变化”的更新影响行数为 0，Service 区分“相同结果”与“资源不存在”：前者保持成功且不通知，后者仍返回 `404`。状态／理由的条件比较与更新在同一 SQL 中完成，避免两个相同审核请求同时生成消息。

首版没有异步重试，因此不增加通用事件去重字段。重复通知控制依托实际业务状态迁移；重新编辑、重新审核、终止后重新购买／接单是新的业务事件，应生成新消息。

## 8. 前端刷新机制

新增 `web/js/notifications.js`，统一管理未读角标和已读写入；新增 `web/js/message-center.js` 管理列表、筛选和分页。页面样式为 `web/css/message-center.css`，沿用现有侧边栏和表单控件风格。

1. 在包含侧边栏的页面完成现有登录身份读取后，通知模块取得当前身份并请求一次未读数量；不另建一套登录判断。
2. 页面可见时每 30 秒刷新未读数量，同一页面使用一套刷新任务；前一次请求完成后再安排下一次请求。
3. 页面隐藏时暂停，重新可见时立即刷新并恢复周期；退出登录或页面卸载时停止。
4. 消息中心的周期刷新只更新全局未读数和 `latestId`，不自动移动当前列表。发现新消息时显示“有新消息，点击刷新”，由用户刷新当前筛选的第 1 页。
5. 轮询网络失败时保留最后一次成功角标，下个周期重试，不连续弹 Toast；消息页可显示“消息更新暂时失败”。收到 `401` 时停止轮询并按现有登录流程处理。
6. 多标签页各自刷新；用户在另一个标签页读过消息，本页在下一次刷新时更新数量。首版不增加跨标签页通信。

消息正文、标题和资源名使用 `textContent` 或现有 `api.escapeHtml` 输出，不作为 HTML 渲染。导航统一按表中目标类型组装项目内页面地址。

## 10. 验收标准

### 10.1 实现完成后的自动化验证

使用临时 SQLite 库和隔离测试数据，不操作现有 `app.db`。

| 检查项 | 预期结果 |
| --- | --- |
| 迁移已有库及重复执行迁移 | 原账号、订单、评价保留，通知表和索引可用，不产生历史通知 |
| 审核通过／驳回 | 发布者收到一条，理由完整；相同审核重复提交不新增；重新编辑再审核可新增 |
| 两类订单创建与交付 | 通知发给正确的另一方，目标绑定当次订单 ID |
| 两类订单完成 | 双方各收到一条，包含评价提示；跑腿直接完成不补送达消息 |
| 终止的四个动作及双方身份互换 | 接收人、事件类型、理由及目标订单均正确 |
| 并发购买／接取、重复完成／处理申请 | 只有成功的状态变更产生对应消息 |
| 事务回滚 | 模拟通知插入失败时业务状态回滚；双方完成通知任一插入失败都回滚 |
| 身份隔离 | 列表与数量只含本人消息；读取、标记他人消息返回 `404`；游客返回 `401` |
| 分类、筛选与分页 | `total` 随筛选变化，`unreadCount` 为全局值，同时间记录顺序稳定 |
| 单条与全部已读 | 重复操作成功；首次已读时间保留；超出水位的新消息仍未读 |
| 历史保留 | 商品／任务软删除后消息仍可读；终止后再次成交，旧通知仍指向旧订单 |

前端自动化检查参数与目标映射、未读角标格式、30 秒刷新及隐藏后暂停、已读写入失败不提前改状态，以及来自消息中心的返回地址保留。

### 10.2 由用户手动验证的页面内容

实现完成后提供以下清单，由用户在浏览器手动验证页面，不自动控制用户电脑操作：

1. 分别以发布者、交易对方和管理员登录，走一遍审核、购买／接单、交付／送达、完成流程，确认通知接收人、文案、角标与订单入口正确。
2. 两类订单分别发起、撤回、拒绝、同意终止；查看原申请通知，确认页面展示当前结果，点击通知本身不会执行业务操作。
3. 从跑腿通知进入订单，再进入任务详情处理；终止后重新接单，确认旧通知仍打开原订单，且不显示进入新一轮任务处理的链接。
4. 在不同分类和“仅未读”下标记消息，翻页并返回；确认筛选、页码及空页处理正确。
5. 点击“全部已读”期间由另一账号触发新通知，确认新消息保持未读；在另一标签页读消息，确认本页下一次刷新更新角标。
6. 切换后台标签页再回来，确认数量刷新；暂时断网检查错误与重试，恢复网络后确认可继续查看。
7. 检查长标题、长审核／申请理由、小窗口和键盘操作下的布局、焦点及按钮状态；检查 0、99、超过 99 条未读的显示。
