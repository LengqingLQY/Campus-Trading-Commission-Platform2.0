## 一、概述

### 1.1 本文档的用途

**本文档定义后端的对外接口契约与内部实现规范。**

| 读者 | 关注章节 |
|---|---|
| 前端组 | 第三章（通用约定）、第四章（接口清单）—— 用于比对双方接口设计是否一致 |
| 后端 | 全部，第五~八章为编码规范 |

接口一经评审确认，任何一方需要改动字段名、参数或返回结构，**先修订本文档，再修改代码，并同步通知对方**。

### 1.2 交付范围

严格对齐需求分析 v1.2 普通用户端第一阶段范围：

- 注册、登录、退出、个人资料查改
- 发布 / 检索 / 排序 / 接取 / 完成 跑腿任务
- 发布 / 检索 / 排序 / 购买 二手商品
- 个人空间：我发布的、我接取的、我购买的

**暂不做**：管理员登录和管理页面、任务/商品审核、软删除/下架、用户管理及所有 `/api/admin/**` 接口。

**其他不做**：真实支付、验证码、即时聊天、推送通知、地图定位、推荐算法、评价体系、复杂筛选。

`user.role`、`audit_status`、`is_deleted` 等数据库字段继续保留用于兼容演示数据和后续扩展，但本阶段不开放管理员能力。由于当前没有审核接口，普通用户创建的任务/商品由 Service 显式写入 `audit_status='approved'`，否则不会被公开视图展示。

### 1.3 技术栈

| 层次 | 选型 | 说明 |
|---|---|---|
| 语言 / JDK | Java 23 | 组长指定 |
| Web 容器 | Tomcat 11.0.9 | 由 Spring Boot 内嵌，无需单独安装 |
| Web 框架 | Spring Boot 3.5.0 | 提供 REST 接口、依赖注入、事务管理 |
| 数据访问 | JdbcTemplate | SQL 由开发者编写，不使用 ORM 自动生成 |
| 数据库 | SQLite 3 | 沿用已定稿的数据库设计，文件为 `backend/db/app.db` |
| 连接池 | HikariCP | Spring Boot 内置 |
| JSON | Jackson | Spring Boot 内置，对象与 JSON 自动互转 |
| 密码哈希 | JDK `javax.crypto` PBKDF2 | 不引入第三方安全库 |
| 构建 | Maven | 依赖统一由 `pom.xml` 管理 |

**数据访问层不使用 MyBatis / JPA 的原因**：数据库设计说明书 §8 已提供全部核心查询语句，JdbcTemplate 可直接复用这些 SQL；引入 ORM 需额外维护映射配置，且会削弱对 SQL 的控制，不利于并发状态更新的精确实现（详见 §6.1）。

### 1.4 与《数据库设计说明书》的关系

**字段名、枚举取值、时间格式、金额格式一律以《数据库设计说明书》为准，本文档不重复定义、不另立标准。**

本文档补充数据库文档未覆盖的部分：接口路径、请求与响应结构、错误码、权限规则、事务边界。

## 二、总体架构

### 2.1 分层架构

```
┌──────────────────────────────────────────────────────────┐
│  客户端    HTML / CSS / JS  ——  调用 /api/* 接口          │
└───────────────────────────┬──────────────────────────────┘
                            │  HTTP + JSON（携带 Cookie）
┌───────────────────────────▼──────────────────────────────┐
│  Interceptor 拦截器    登录检查                             │
├──────────────────────────────────────────────────────────┤
│  Controller 控制层     接收参数、校验格式、取登录态、返回     │
│                        ★ 不写业务规则，不访问数据库          │
├──────────────────────────────────────────────────────────┤
│  Service 业务层        业务规则、状态判断、★ 事务边界        │
├──────────────────────────────────────────────────────────┤
│  DAO 数据访问层        编写 SQL，一个方法完成一件事          │
│                        ★ 不做业务判断                      │
├──────────────────────────────────────────────────────────┤
│  JdbcTemplate + HikariCP                                 │
└───────────────────────────┬──────────────────────────────┘
                            │
                  ┌─────────▼─────────┐
                  │  SQLite  app.db   │  5 表 + 2 视图
                  │  约束为最后一道防线 │
                  └───────────────────┘
```

**每层只能调用其下一层**：Controller 不得直接调用 DAO，Service 不得引用 `HttpServletRequest`。

### 2.2 一次请求的数据流动

以「用户接取 12 号任务」为例：

```
① 客户端
   POST /api/tasks/12/accept
                    │
② Interceptor      ▼
   从 Cookie 中的 JSESSIONID 取出 session 中的 user
   未登录 → 直接返回 401，请求不再向下传递
                    │  user = {id:3, role:'user'}
③ Controller       ▼
   路径变量 id 解析为 12，调用 taskService.acceptTask(12, 3)
                    │
④ Service          ▼  开启事务
   a. UPDATE task SET status='accepted'
       WHERE id=12 AND status='open' AND audit_status='approved' AND is_deleted=0
      → 受影响行数为 0 说明任务已被他人接取 → 回滚，返回 409
   b. INSERT INTO task_order (task_id, publisher_id, accepter_id) VALUES (12, ?, 3)
      → 违反 UNIQUE 或 CHECK 约束时抛异常 → 事务自动回滚
   提交事务
                    │
⑤ Controller       ▼
   Result 对象序列化为 JSON
                    │
⑥ 客户端           ▼
   {"code":0,"msg":"ok","data":{"orderId":5}}
```

**关键点在 ④a**：状态判断写入 `UPDATE` 的 `WHERE` 子句，通过受影响行数判定成败，而非「先查询状态再更新」。后者在并发场景下存在时间窗（详见 §6.1）。

## 三、通用约定

### 3.1 统一响应格式

所有接口无论成功或失败，均返回同一结构：

```json
{
  "code": 0,
  "msg": "ok",
  "data": { }
}
```

| 字段 | 说明 |
|---|---|
| `code` | `0` 表示成功；非 0 表示失败，其值等于 HTTP 状态码 |
| `msg` | 面向用户的中文提示，成功时固定为 `"ok"` |
| `data` | 成功时的业务数据；失败时为 `null` |

失败示例：`{ "code": 409, "msg": "任务已被接取", "data": null }`

**HTTP 状态码与 `code` 保持一致**：失败时 HTTP 也返回对应的 4xx，不统一返回 200。

### 3.2 错误码表

| code | 含义 | 触发条件 |
|---|---|---|
| `0` | 成功 | — |
| `400` | 参数错误 | 必填项为空、金额为负、枚举值非法、时间格式错误 |
| `401` | 未登录 / 账号密码错误 | 未登录调用需登录接口、session 过期、登录密码错误 |
| `403` | 无权限 | 操作他人资源、接取自己的任务、购买自己的商品、非指定参与方操作订单 |
| `404` | 资源不存在 | id 不存在、已被软删除、未过审内容对非所有者 |
| `409` | 状态冲突 | 账号重复、任务已被接取、商品已售出、当前状态不允许该操作 |
| `500` | 服务器错误 | 未预期的异常、数据库错误 |

> `404` 将「不存在」与「未过审 / 已删除」合并返回，避免通过遍历 id 探测已删除内容的存在性。

### 3.3 鉴权方式：Session + Cookie

- 登录成功后，后端将用户对象存入 `HttpSession`，响应中返回 `JSESSIONID` Cookie
- 此后每次请求依据该 Cookie 识别当前用户
- 退出登录调用 `POST /api/logout`，后端销毁 session
- session 默认 30 分钟不活动后过期，过期后接口返回 `401`

**后端一律从 session 获取当前用户身份，不接受请求参数中传入的 userId**（详见 §7.3）。当前版本没有管理员权限拦截器。

### 3.4 请求格式

| 类型 | 约定 |
|---|---|
| 请求体 | JSON，`Content-Type: application/json`，UTF-8 |
| 查询参数 | URL query，如 `?keyword=打印&sort=amount_desc&page=1` |
| 路径参数 | 如 `/api/tasks/12/accept` 中的 `12` |
| 字符编码 | 全程 UTF-8 |

### 3.5 时间与金额

沿用《数据库设计说明书》§5：

- **时间**：统一为 `'YYYY-MM-DD HH:MM:SS'` 字符串，如 `2026-08-26 14:30:00`。POJO 中以 `String` 接收和返回，不转换为 `Date`，避免时区问题
- **金额**：`double`，单位元
- 后端对入参时间做格式校验，不符合格式返回 `400`

### 3.6 分页

所有列表接口统一支持分页：

| 参数 | 默认值 | 说明 |
|---|---|---|
| `page` | `1` | 页码，从 1 开始 |
| `size` | `10` | 每页条数，最大 50 |

列表接口的 `data` 统一为：

```json
{ "list": [ ... ], "total": 37, "page": 1, "size": 10 }
```

### 3.7 排序参数白名单

`sort` 仅接受下列固定值，传入其他值按默认处理：

| 列表 | 可选值 | 默认 |
|---|---|---|
| 任务 | `time_desc` `time_asc` `amount_desc` `amount_asc` | `time_desc` |
| 商品 | `time_desc` `time_asc` `price_desc` `price_asc` | `time_desc` |

### 3.8 接口路径划分约定

**公开接口（无需登录）统一使用 `/api/public/` 前缀**，需登录接口直接挂在 `/api/` 下。这样拦截器在路径层面即可区分两类接口，无需在 Controller 内重复判断登录。当前版本不定义 `/api/admin/**`。

| 前缀 | 含义 |
|---|---|
| `/api/public/**` | 公开，任何人可访问（浏览列表、详情、注册、登录） |
| `/api/**`（除 public 外） | 需登录 |

## 四、接口清单

> 「权限」：**公开** = 无需登录；**登录** = 需登录。管理员接口不属于本版本。

### 4.1 账号与个人资料（5 个）

#### ① 注册

| | |
|---|---|
| 路径 | `POST /api/register` |
| 权限 | 公开 |
| 对应需求 | P0-01 |

请求体：
```json
{
  "account": "bob2",  "password": "bob123",  "username": "小明",
  "qq": "123456",     "wechat": "wx_ming",   "phone": "13800138000"
}
```

| 字段 | 必填 | 校验 |
|---|---|---|
| `account` | ✅ | 非空，不可重复 |
| `password` | ✅ | 非空，长度 ≥ 6 |
| `username` | ✅ | 非空 |
| `qq` / `wechat` / `phone` | ❌ | 可空、自由填写，不做格式与真实性校验（需求明确要求） |

成功：`{"code":0,"msg":"ok","data":{"id":5}}`
失败：`400` 必填项为空或密码过短；`409` 账号已存在

> **安全要求**：`role` 由服务端固定为 `'user'`，不接受前端传入，否则任何人可注册为管理员。密码仅存储 PBKDF2 哈希（P0-05）。

#### ② 登录

| | |
|---|---|
| 路径 | `POST /api/login` |
| 权限 | 公开 |
| 对应需求 | P0-02 |

请求体：`{"account":"alice","password":"alice123"}`

成功：
```json
{"code":0,"msg":"ok","data":{"id":2,"account":"alice","username":"爱丽丝","role":"user"}}
```

失败：`401` 账号或密码错误

> 账号不存在与密码错误返回相同提示，不暴露账号是否存在。`role` 字段保留用于兼容数据库；本版本只验收 `role=user` 的普通用户闭环，不提供管理员页面或管理员接口。

#### ③ 退出

| | |
|---|---|
| 路径 | `POST /api/logout` |
| 权限 | 登录 |

成功：`{"code":0,"msg":"ok","data":null}`，后端销毁 session

#### ④ 查看个人资料

| | |
|---|---|
| 路径 | `GET /api/users/me` |
| 权限 | 登录 |
| 对应需求 | P0-03 |

成功：
```json
{"code":0,"msg":"ok","data":{
  "id":2,"account":"alice","username":"爱丽丝",
  "qq":"10001","wechat":"wx_alice","phone":"13900139000",
  "role":"user","createdAt":"2026-08-25 18:22:38"}}
```

> `passwordHash` 不出现在任何响应中。

#### ⑤ 修改个人资料

| | |
|---|---|
| 路径 | `PUT /api/users/me` |
| 权限 | 登录（仅限本人） |
| 对应需求 | P0-03 |

请求体（字段可选，仅传需修改项）：
```json
{"username":"新昵称","qq":"10002","wechat":"","phone":"13900139001",
 "oldPassword":"alice123","newPassword":"alice456"}
```

| 规则 |
|---|
| `account` 不可修改，传入则忽略 |
| `role` 不可修改，传入则忽略 |
| 修改密码时 `oldPassword` 与 `newPassword` 必须同时传入，且旧密码校验通过 |

成功：`{"code":0,"msg":"ok","data":null}`
失败：`400` 新密码过短；`401` 旧密码错误

### 4.2 跑腿任务（6 个）

#### ① 任务列表

| | |
|---|---|
| 路径 | `GET /api/public/tasks` |
| 权限 | 公开 |
| 对应需求 | §4.2 查看、§4.4 检索排序 |

查询参数：

| 参数 | 必填 | 说明 |
|---|---|---|
| `keyword` | ❌ | 关键词，同时匹配 `title` 与 `description` |
| `sort` | ❌ | `time_desc`(默认) `time_asc` `amount_desc` `amount_asc` |
| `page` / `size` | ❌ | 分页，默认 1 / 10 |

成功：
```json
{"code":0,"msg":"ok","data":{
  "list":[{
    "id":1,"title":"帮取快递","description":"菜鸟驿站取个箱子",
    "pickup":"三号门菜鸟驿站","delivery":"12栋 305","deadline":"2026-08-27 18:00:00",

    "createdAt":"2026-08-25 18:22:38"
  }],
  "total":12,"page":1,"size":10}}
```

> 查询走 `v_public_task` 视图，已自动过滤 `audit_status='approved' AND is_deleted=0`。
> 列表不返回 `contact`，需进入详情才提供，减少信息暴露面。

#### ② 发布任务

| | |
|---|---|
| 路径 | `POST /api/tasks` |
| 权限 | 登录 |
| 对应需求 | §4.2 发布 |

请求体：
```json
{"title":"帮取快递","description":"菜鸟驿站取个箱子",
 "pickup":"三号门菜鸟驿站","delivery":"12栋 305",
 "deadline":"2026-08-27 18:00:00","amount":5,"contact":"QQ 123456"}
```

| 字段 | 必填 | 校验 |
|---|---|---|
| `title` `pickup` `delivery` | ✅ | 非空 |
| `description` `contact` | ❌ | 默认 `""` |
| `deadline` | ❌ | 格式 `YYYY-MM-DD HH:MM:SS` |
| `amount` | ❌ | ≥ 0，默认 0 |

成功：`{"code":0,"msg":"ok","data":{"id":13}}`

> `publisher_id` 取自 session，不接受前端传入；由于本版本不实现管理员审核，落库时由 Service 显式写入 `audit_status='approved'`、`status='open'`，新发布内容可以直接进入公开列表。

#### ③ 任务详情

| | |
|---|---|
| 路径 | `GET /api/public/tasks/{id}` |
| 权限 | 公开 |

成功：返回该任务全部字段及 `publisherName`；已过审的才返回 `contact`。

若请求者为发布者本人，额外返回 `auditStatus` 与 `auditRemark`（驳回理由）。

#### ④ 接取任务

| | |
|---|---|

## 五、分层设计规范

### 5.1 各层职责边界

| 层 | 职责 | 禁止事项 |
|---|---|---|
| **Controller** | 接收请求、参数格式校验、从 session 取当前用户、调用 Service、返回 `Result` | ❌ 编写业务规则<br>❌ 直接调用 DAO<br>❌ 编写 SQL |
| **Service** | 业务规则判断、状态流转、**事务边界**、组装返回数据 | ❌ 引用 `HttpServletRequest` / `HttpSession`<br>❌ 拼装 JSON |
| **DAO** | 编写 SQL、参数化查询、结果映射为 POJO | ❌ 做业务判断<br>❌ 抛出业务异常 |
| **POJO** | 纯数据对象，与表一一对应 | ❌ 编写逻辑 |
| **DTO** | 接口出入参专用对象 | — |

**当前用户的传递方式**：Controller 从 session 取出 `User`，将 `userId` 作为参数传给 Service。Service 方法签名形如 `acceptTask(int taskId, int currentUserId)`，使其不依赖 Web 环境，便于单元测试。

### 5.2 DAO 编写规范

```java
@Repository
public class TaskDAO {

    @Autowired
    private JdbcTemplate jdbc;

    // 查询单条：使用 query 取列表后取首条，不使用 queryForObject
    // （queryForObject 查不到会抛异常，而"查不到"属于正常业务分支）
    public Task findById(int id) {
        List<Task> list = jdbc.query("SELECT * FROM task WHERE id = ?",
                new BeanPropertyRowMapper<>(Task.class), id);
        return list.isEmpty() ? null : list.get(0);
    }

    // 查询列表：SQL 复用《数据库设计说明书》§8 的查询片段
    public List<Task> findPublic(String keyword, String orderBy, int offset, int size) {
        String sql = "SELECT t.*, u.username AS publisherName "
                   + "  FROM v_public_task t JOIN user u ON u.id = t.publisher_id "
                   + " WHERE t.title LIKE ? ESCAPE '\\' OR t.description LIKE ? ESCAPE '\\' "
                   + " ORDER BY " + orderBy          // orderBy 必须来自白名单，见 §5.3
                   + " LIMIT ? OFFSET ?";
        String p = likePattern(keyword);
        return jdbc.query(sql, new BeanPropertyRowMapper<>(Task.class), p, p, size, offset);
    }

    // 状态更新：条件写入 WHERE，返回受影响行数交由 Service 判断
    public int accept(int taskId) {
        return jdbc.update(
            "UPDATE task SET status='accepted', updated_at=datetime('now','localtime') "
          + " WHERE id=? AND status='open' AND audit_status='approved' AND is_deleted=0",
            taskId);
    }
}
```

**字段映射规则**：`BeanPropertyRowMapper` 自动完成下划线转驼峰（`password_hash` → `passwordHash`）。SQL 中手写的别名需直接写为驼峰形式（如 `AS publisherName`）。

### 5.3 安全编码红线

**① SQL 一律参数化，禁止字符串拼接**

```java
// 正确
jdbc.query("SELECT * FROM user WHERE account = ?", mapper, account);

// 错误：存在 SQL 注入风险
jdbc.query("SELECT * FROM user WHERE account = '" + account + "'", mapper);
```

**② 排序字段必须走白名单**

`ORDER BY` 后不支持 `?` 占位符，只能拼接字符串，因此必须限定取值：

```java
private static final Map<String, String> TASK_ORDER = Map.of(
    "time_desc",   "t.created_at DESC",
    "time_asc",    "t.created_at ASC",
    "amount_desc", "t.amount DESC",
    "amount_asc",  "t.amount ASC"
);
String orderBy = TASK_ORDER.getOrDefault(sort, "t.created_at DESC");
```

**③ 关键词检索需转义**（`%` 与 `_` 是 LIKE 的通配符）

```java
private static String likePattern(String keyword) {
    if (keyword == null) return "%";
    String esc = keyword.replace("\\", "\\\\").replace("%", "\\%").replace("_", "\\_");
    return "%" + esc + "%";
}
```

## 六、核心业务流程与事务

### 6.1 接取任务 —— 三层防护

**问题**：两个用户同时接取同一任务时，如何保证只有一人成功。

**错误写法**（先查后写，存在时间窗）：

```java
Task task = taskDAO.findById(id);
if (task.getStatus().equals("open")) {     // 两个线程可能同时判断为 true
    taskDAO.updateStatus(id, "accepted");
    taskOrderDAO.insert(...);              // 结果插入两条记录
}
```

**正确写法**：

```java
@Service
public class TaskService {

    @Transactional                          // 方法内在同一事务，抛异常自动全部回滚
    public Result acceptTask(int taskId, int currentUserId) {

        // 防护一：业务规则校验
        Task task = taskDAO.findById(taskId);
        if (task == null || task.getIsDeleted() == 1
                || !"approved".equals(task.getAuditStatus())) {
            return Result.fail(404, "任务不存在");
        }
        if (task.getPublisherId() == currentUserId) {
            return Result.fail(403, "不能接取自己发布的任务");
        }

        // 防护二：状态判断写入 UPDATE 的 WHERE，由受影响行数决定成败
        //          并发时数据库保证只有一个线程能更新成功，另一个得到 0
        int rows = taskDAO.accept(taskId);
        if (rows == 0) {
            return Result.fail(409, "任务已被接取");
        }

        // 防护三：数据库约束兜底
        //          task_order.task_id 的 UNIQUE 与 CHECK(accepter_id <> publisher_id)
        //          即便上层逻辑有误，此处仍会抛出约束异常，由全局异常处理转为 409（§8）
        int orderId = taskOrderDAO.insert(taskId, task.getPublisherId(), currentUserId);

        return Result.ok(Map.of("orderId", orderId));
    }
}
```

`@Transactional` 保证方法正常结束时提交、抛出运行时异常时回滚，因此不会出现「已更新 task 状态但未插入 task_order」的半截数据。

> **`@Transactional` 的两个限制**：
> 1. 仅对 public 方法生效
> 2. 同一个类内部方法互相调用不生效（`this.methodB()` 绕过了代理），需拆分到不同 Service 类

### 6.2 送达与确认

```
                任务被接取
        status=accepted, order.status=accepted
                     │
                     │ 接单方 PUT /tasks/{id}/deliver
                     ▼
        status=delivered, order.status=delivered, delivered_at=now
                     │
                     │ 发布者 PUT /tasks/{id}/complete
                     ▼
        status=completed, order.status=completed, finished_at=now
```

两步均需在 `@Transactional` 中同时更新 `task` 与 `task_order` 两张表。

权限判断同样写入 SQL 的 `WHERE`，而非先查询再判断：

```java
// 仅接取人本人、且当前状态为 accepted 时才能更新
int rows = jdbc.update(
    "UPDATE task_order SET status='delivered', delivered_at=datetime('now','localtime') "
  + " WHERE task_id=? AND accepter_id=? AND status='accepted'", taskId, currentUserId);
if (rows == 0) return Result.fail(409, "当前状态不允许该操作");
```

本版本不提供管理员强制结单路径；若发布者长期不确认，任务保留在 `delivered`，由后续管理员模块再补充处理。

### 6.3 购买商品

结构与接取任务一致，三层防护一一对应：

| | 接取任务 | 购买商品 |
|---|---|---|
| 业务校验 | 不能接取自己发布的 | 不能购买自己发布的 |
| WHERE 条件 | `status='open'` | `status='on_sale'` |
| 数据库兜底 | `UNIQUE(task_id)` + `CHECK(accepter_id<>publisher_id)` | `UNIQUE(product_id)` + `CHECK(buyer_id<>seller_id)` |

**额外要求**：插入 `product_order` 时将 `product.price` 复制到 `product_order.price` 作为成交价快照。

### 6.4 审核与软删除（延期能力）

本版本没有审核、驳回、软删除或下架接口。数据库继续保留 `audit_status`、`audit_remark`、`is_deleted`、`deleted_by`、`deleted_at`，供演示数据兼容和后续管理员模块使用。

当前用户发布任务/商品时，Service 必须显式写入 `audit_status='approved'`；公开查询仍通过 `v_public_task` / `v_public_product` 过滤 `audit_status='approved' AND is_deleted=0`。后续恢复管理员模块时，审核只修改 `audit_status`，软删除只更新 `is_deleted=1`，不改变业务 `status`。

### 6.5 SQLite 的写并发处理

SQLite 为单文件数据库，同一时刻仅允许一个写事务。内嵌 Tomcat 为多线程模型，并发写入时后到的线程会抛出 `SQLITE_BUSY`。

已在 `application.properties` 中处理：

```properties
# 获取写锁失败时等待 5 秒再报错，而非立即失败
spring.datasource.url=jdbc:sqlite:../backend/db/app.db?busy_timeout=5000

# SQLite 外键默认关闭，每条连接均需开启（《数据库设计说明书》§7.1）
# connection-init-sql 在连接池新建连接时自动执行
spring.datasource.hikari.connection-init-sql=PRAGMA foreign_keys=ON

# 单文件数据库，连接池过大反而加剧写锁竞争
spring.datasource.hikari.maximum-pool-size=5
```

> `PRAGMA foreign_keys=ON` 为必需项。遗漏将导致 schema 中所有 `REFERENCES` 失效，可写入不存在的外键值。
>
> 上述配置可满足本项目的并发规模。更高并发场景需改用 WAL 模式或迁移至 MySQL。

### 7.1 拦截器配置

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Override
    public void addInterceptors(InterceptorRegistry registry) {

        // 登录检查：拦截所有 /api/**，放行公开接口
        registry.addInterceptor(new AuthInterceptor())
                .addPathPatterns("/api/**")
                .excludePathPatterns(
                        "/api/register", "/api/login",
                        "/api/public/**");     // 公开接口统一前缀

    }

```

`AuthInterceptor`：session 中无 `user` 时直接写回 `{"code":401,"msg":"请先登录"}` 并 `return false`，请求不再向下传递。

> 公开接口统一走 `/api/public/` 前缀，与需登录接口在路径层面完全分开，因此 `POST /api/tasks`（发布，需登录）能被 `AuthInterceptor` 正常拦截，无需在 Controller 内重复判断登录。

### 7.2 权限矩阵

| 操作 | 游客 | 登录用户 | 资源所有者 |

| 注册、登录 | ✅ | — | — |
| 发布任务 / 商品 | ❌ | ✅ | — |
| 接取任务 | ❌ | ✅ | ❌ 自己发布的不可 |
| 购买商品 | ❌ | ✅ | ❌ 自己发布的不可 |
| 标记已送达 | ❌ | ❌ | ✅ 仅接单方 |
| 确认完成 | ❌ | ❌ | ✅ 仅发布者 |
| 查改自己的资料 | ❌ | ✅ | ✅ |
| 查看未过审 / 已驳回内容 | ❌ | ❌ | ✅ 仅自己的 |

> 系统中不区分「发布者」与「接单者」角色。任一普通用户均可同时发布、接取、出售、购买；限制仅针对单条内容（不能接取或购买自己发布的内容）。管理员角色和管理权限不属于本版本。

### 7.3 三条强制原则

1. **当前用户身份一律从 session 获取，不接受请求参数中的 userId**，否则修改参数即可冒充他人
2. **`role` 不接受前端传入**。注册接口固定为 `'user'`，改资料接口忽略 `role` 字段
3. **前端隐藏按钮不构成权限控制**。需求 §6 明确要求「后端要再次检查状态，不能只依赖按钮隐藏」，每个写操作接口均须自行校验

## 八、异常处理与日志

### 8.1 统一异常处理

使用 `@RestControllerAdvice` 集中将异常转换为统一响应格式，Controller 内不编写 `try-catch`：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    // 业务异常：Service 主动抛出
    @ExceptionHandler(BizException.class)
    public ResponseEntity<Result> handleBiz(BizException e) {
        return ResponseEntity.status(e.getCode()).body(Result.fail(e.getCode(), e.getMessage()));
    }

    // 唯一约束冲突：重复接取、重复购买、账号重复
    @ExceptionHandler(DuplicateKeyException.class)
    public ResponseEntity<Result> handleDuplicate(DuplicateKeyException e) {
        return ResponseEntity.status(409).body(Result.fail(409, "操作冲突，请刷新后重试"));
    }

    // CHECK / 外键约束冲突：自接取、自购买、非法枚举值、负数金额
    @ExceptionHandler(DataIntegrityViolationException.class)
    public ResponseEntity<Result> handleIntegrity(DataIntegrityViolationException e) {
        log.warn("数据库约束拦截: {}", e.getMessage());
        return ResponseEntity.status(409).body(Result.fail(409, "数据不符合要求"));
    }

    // 兜底：未预期的异常
    @ExceptionHandler(Exception.class)
    public ResponseEntity<Result> handleOther(Exception e) {
        log.error("未处理异常", e);                            // 完整堆栈仅写入日志
        return ResponseEntity.status(500).body(Result.fail(500, "系统繁忙，请稍后重试"));
    }
}
```

> 异常堆栈不得返回给客户端，避免泄漏表名、字段名与文件路径。堆栈只写日志。

### 8.2 数据库约束到 HTTP 状态码的映射

《数据库设计说明书》§9 已验证的 9 类约束，对应到接口层：

| 数据库拦截的场景 | 约束类型 | 返回 | msg |
|---|---|---|---|
| 注册重复账号 | UNIQUE | `409` | 账号已存在 |
| 同一任务被两人接取 | UNIQUE | `409` | 任务已被接取 |
| 同一商品被重复购买 | UNIQUE | `409` | 商品已售出 |
| 接取自己发布的任务 | CHECK | `403` | 不能接取自己发布的任务 |
| 购买自己发布的商品 | CHECK | `403` | 不能购买自己的商品 |
| 写入枚举外的状态值 | CHECK | `400` | 参数值不合法 |
| 写入负数金额 | CHECK | `400` | 金额不能为负数 |
| 引用不存在的用户 id | FOREIGN KEY | `500` | 系统繁忙（属于程序缺陷，不应发生） |

> 正常情况下上述错误在 Service 层即被拦截并返回精确提示。触发数据库约束说明业务层逻辑存在遗漏。**数据库约束是第二道防线，不是第一道。**

### 8.3 日志

开发阶段在 `application.properties` 中开启 SQL 日志便于排查，交付演示时可关闭：

```properties
logging.level.org.springframework.jdbc.core=DEBUG
```

**日志中禁止输出**：明文密码、`password_hash`、完整的用户联系方式。

## 九、开发计划

### 9.1 模块交付顺序

按依赖关系与联调优先级排序：

| 顺序 | 模块 | 接口 | 说明 |
|:---:|---|---|---|
| 1 | 基础设施 | `Result` / 拦截器 / 异常处理 / `PasswordUtil` | 全部接口的公共依赖 |
| 2 | 账号 | 注册、登录、退出、查改资料（5 个） | 其余模块的测试前提 |
| 3 | 任务列表与发布 | `GET /api/public/tasks`、`POST /api/tasks`、详情（3 个） | 主页面依赖 |
| 4 | 商品列表与发布 | `GET /api/public/products`、`POST /api/products`、详情（3 个） | 结构与任务平行 |
| 5 | 交易动作 | 接取、送达、完成、购买（4 个） | 涉及事务与并发，需重点测试 |
| 6 | 个人空间 | `GET /api/me/*`（2 个） | 纯查询，依赖前序数据 |

第 2 步完成后即可交付联调，无需等待全部接口完成。

### 9.3 评审结论

2026-08-27 本次契约调整确认：

| # | 议题 | 结论 |
|:---:|---|---|
| 1 | 任务完成方式 | 采用「两步确认 + 一步直达」（§4.2⑥）：正常走「送达 → 确认」两步，发布者可从 `accepted` 直接完成 |
| 2 | 公开接口前缀 | 公开接口统一使用 `/api/public/` 前缀，与需登录接口在路径上区分 |
| 3 | 端口分配 | 后端使用 8081，8080 留给前端主界面 |
| 4 | 当前交付边界 | 只交付普通用户端 17 个接口；管理员登录、审核、删除、用户管理和 `/api/admin/**` 延期 |
| 5 | 无管理员时的发布 | 普通用户创建任务/商品时显式写入 `audit_status='approved'`，保留审核字段供后续扩展 |

## 附录 B：SQLite 类型与 Java 类型对照

| 数据库类型 | Java 类型 | 说明 |
|---|---|---|
| `INTEGER`（主键 / 外键） | `Integer` | 使用包装类型而非 `int`，因可能为 `null` |
| `INTEGER`（`is_deleted` 0/1） | `Integer` | 判断写作 `isDeleted == 1`，不使用 `boolean` |
| `TEXT` | `String` | |
| `TEXT`（时间） | `String` | 不转换为 `Date` / `LocalDateTime`，直接透传 `'YYYY-MM-DD HH:MM:SS'` |
| `REAL`（金额） | `Double` | 单位元 |

**命名对照**：数据库 `password_hash` ↔ POJO `passwordHash` ↔ JSON `passwordHash`，由 `BeanPropertyRowMapper` 自动完成下划线转驼峰。
