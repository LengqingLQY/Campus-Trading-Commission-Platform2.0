## 1. 目标与术语

1. 商品“删除”固定解释为软删除：数据仍保留在 `product` 表，仅从普通前端查询中隐藏。
2. 二手订单处于 `created` 或 `delivered` 时，买卖任一方可以发起终止申请。
3. 终止不是单方立即生效：发起方可以撤回，另一方可以拒绝或同意；只有另一方同意后订单才进入 `cancelled`，商品才恢复 `on_sale`。
4. 已终止订单永久保留，原买卖双方仍可查看；商品恢复待售后允许产生新的订单。

本文中的“终止申请”使用独立记录，不把 `product_order.status` 改成临时状态。订单在申请待处理期间仍保持原来的 `created` 或 `delivered`，由待处理记录控制可用动作。

## 2. 商品删除必须是软删除

### 2.1 禁止操作

发布者删除商品时，后端不得执行以下操作：

```sql
DELETE FROM product WHERE id = :productId;
DELETE FROM product_order WHERE product_id = :productId;
```

### 2.2 正确操作

继续使用前置增量中的 `DELETE /api/products/{id}`，但其语义是执行更新：

```sql
UPDATE product
SET is_deleted = 1,
    deleted_by = :currentUserId,
    deleted_at = datetime('now', 'localtime'),
    updated_at = datetime('now', 'localtime')
WHERE id = :productId
  AND seller_id = :currentUserId
  AND is_deleted = 0
  AND status IN ('on_sale', 'completed');
```

- `status` 保留真实业务状态，不写入伪造的 `deleted` 状态。
- 所有关联订单、成交价快照、买卖双方和时间字段保持不变。
- 普通公开查询及卖家的在架记录继续通过 `is_deleted = 0` 隐藏软删除数据。
- 后续若增加恢复能力，应通过独立恢复接口把 `is_deleted` 改回 `0`，并清空或另行保留恢复审计；本次不增加恢复按钮或恢复接口。

## 3. 双向终止状态流

```text
created / delivered
        │ 任一方发起
        ▼
原订单状态不变 + termination_request=pending
        ├─ 发起方撤回 ───────────────→ 原订单状态继续
        ├─ 另一方拒绝 ───────────────→ 原订单状态继续
        └─ 另一方同意 ─→ order=cancelled + product=on_sale
```

约束：

- `completed`、`cancelled` 订单不能发起终止申请。
- 同一订单同时最多存在一条 `pending` 申请。
- 待处理期间不得执行 `/deliver` 或 `/complete`；这两个既有接口必须返回 `409`。
- 发起人不能同意或拒绝自己的申请，另一方不能替发起人撤回。

## 4. 数据库增量设计

### 4.1 新增终止申请记录表

建议表名：`product_order_termination_request`。

```sql
CREATE TABLE product_order_termination_request (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    order_id      INTEGER NOT NULL REFERENCES product_order(id),
    requester_id  INTEGER NOT NULL REFERENCES user(id),
    reason        TEXT    NOT NULL,
    status        TEXT    NOT NULL DEFAULT 'pending'
                          CHECK (status IN ('pending', 'approved', 'rejected', 'withdrawn')),
    responder_id  INTEGER REFERENCES user(id),
    created_at    TEXT    NOT NULL DEFAULT (datetime('now', 'localtime')),
    resolved_at   TEXT
);

CREATE UNIQUE INDEX uq_product_order_pending_termination
ON product_order_termination_request(order_id)
WHERE status = 'pending';
```

建议给 `product_order` 增加 `cancelled_at TEXT`，用来直接记录订单进入 `cancelled` 的时间；终止申请表仍保留完整申请与响应审计。

### 4.2 必须调整商品订单唯一约束

现有 `product_order.product_id UNIQUE` 会导致商品终止后即使恢复 `on_sale`，也无法插入第二条订单。数据库迁移必须：

1. 重建 `product_order`，移除列级 `UNIQUE(product_id)`；SQLite 不能直接删除该约束，迁移时必须复制并保留所有旧数据和原 id。
2. 新建只限制“未终止订单”的部分唯一索引：

```sql
CREATE UNIQUE INDEX uq_product_order_non_cancelled_product
ON product_order(product_id)
WHERE status <> 'cancelled';
```

这样可以保留多条历史 `cancelled` 订单，同时保证同一商品最多有一条进行中或已完成的非终止订单。

### 4.3 关联查询调整

- `ProductOrderDAO.findByProductId` 必须明确查询最新的非 `cancelled` 订单，不能再假定一个商品永远只有一条订单。
- 卖家商品记录查询必须避免因多条历史订单导致同一商品重复，可关联最新非终止订单；没有非终止订单时可关联最新一条终止记录用于历史展示。
- 买家订单历史按订单维度保留，每条已终止订单仍可查看。

## 5. 现有查询接口增量字段

### 5.1 订单详情

`GET /api/product-orders/{id}` 在存在待处理申请时新增：

```json
{
  "id": 31,
  "productId": 12,
  "status": "created",
  "viewerRole": "seller",
  "terminationRequest": {
    "id": 8,
    "status": "pending",
    "requesterRole": "buyer",
    "requesterName": "李同学",
    "reason": "近期不在学校，无法按约定时间交易",
    "createdAt": "2026-09-25 14:20:00"
  }
}
```

- 没有待处理申请时，`terminationRequest` 为 `null`。
- `requesterRole` 由后端按订单买卖双方计算，不接受前端指定。
- 订单已终止时返回 `status='cancelled'`、`cancelledAt`；待处理申请应为 `null`。

### 5.2 主界面交易待办

`GET /api/me/products?type=published|bought` 的进行中订单项同步返回相同结构的 `terminationRequest`，供主界面提示：

- 发起方：`待对方确认终止`；
- 另一方：`待处理终止申请`，并作为需要当前用户操作的待办置顶。

## 6. 新增接口

所有接口均要求登录，且当前用户必须是订单买家或卖家。身份只能从 Session 获取。

### 6.1 发起终止申请

```http
POST /api/product-orders/{id}/termination-request
Content-Type: application/json

{
  "reason": "时间无法协调，希望终止本次交易"
}
```

- `reason` 去除首尾空白后必须为 2～200 字。
- 仅 `created`、`delivered` 可发起。
- 已有 `pending` 申请返回 `409`。

成功返回 HTTP `200`：

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "id": 8,
    "status": "pending"
  }
}
```

### 6.2 发起方撤回

```http
DELETE /api/product-orders/{id}/termination-request
```

- 仅申请发起方可操作。
- 将申请 `pending -> withdrawn`，写入 `resolved_at`；订单和商品状态不变。

### 6.3 另一方拒绝

```http
PUT /api/product-orders/{id}/termination-request/reject
```

- 仅非发起方的交易参与者可操作。
- 将申请 `pending -> rejected`，写入 `responder_id/resolved_at`；订单和商品状态不变，原交易动作恢复。

### 6.4 另一方同意

```http
PUT /api/product-orders/{id}/termination-request/approve
```

- 仅非发起方的交易参与者可操作。
- 成功返回：

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "orderId": 31,
    "orderStatus": "cancelled",
    "productId": 12,
    "productStatus": "on_sale"
  }
}
```

## 7. 同意终止的原子事务

同意操作必须在同一数据库事务内完成：

1. 锁定或条件读取唯一的 `pending` 申请，确认当前用户是订单另一方。
2. 条件更新申请 `pending -> approved`，写入 `responder_id/resolved_at`。
3. 条件更新订单 `created|delivered -> cancelled`，写入 `cancelled_at`。
4. 条件更新商品 `sold -> on_sale` 和 `updated_at`。
5. 任一步更新行数不是 `1`，整体回滚并返回 `409`。

不得删除旧订单，不得把旧订单重置成 `created`，不得覆盖原买家、成交价、`created_at` 或 `delivered_at`。商品再次售出时应插入一条新的 `product_order`。

`deliver`、`complete`、`approve` 三类动作必须通过条件更新和事务互斥：如果终止申请已待处理，交付/收货失败；如果订单已完成，终止同意失败。任何并发结果都不能出现“订单 completed 但商品 on_sale”。

## 8. 错误响应

| HTTP / code | msg 建议值 | 场景 |
|---:|---|---|
| `400` | `终止原因需为 2～200 字` | 原因不合法 |
| `401` | `请先登录` | 未登录 |
| `403` | `无权限操作该终止申请` | 非交易双方、错误角色操作 |
| `404` | `订单不存在` / `终止申请不存在` | 资源不存在 |
| `409` | `当前订单状态不允许终止` | 已完成或已终止 |
| `409` | `已有待处理的终止申请` | 重复发起 |
| `409` | `订单状态已变化，请刷新后重试` | 并发动作冲突 |

失败继续使用统一结构，`data` 为 `null`。

## 9. 前端交互验收

1. `created`、`delivered` 订单页均显示“申请终止交易”，并明确提示需要另一方同意。
2. 发起表单要求填写 2～200 字原因。
3. 发起后，发起方看到“等待对方处理”和“撤回终止申请”；另一方看到原因、“同意终止并恢复在售”和“拒绝，继续交易”。
4. 有待处理申请时不显示交付或确认收货动作。
5. 同意成功后订单显示“交易已终止”，商品详情与公开列表显示 `on_sale`，旧订单记录仍可查看。
6. 拒绝或撤回后订单保持原状态，原交付/收货动作恢复。
7. 主界面把需要当前用户处理的终止申请置顶。
8. 商品删除后数据库记录仍存在，只从普通页面隐藏；本次不提供恢复按钮。
